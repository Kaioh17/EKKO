EKKO architecture

A local voice assistant with a desktop app. Known commands run through fixed, hand-written rules. Anything open-ended goes to an LLM you choose, with failover. This page covers the whole system end to end, where dev and production differ, how memory works, and how LLM calls are made.

1. System map

Three cooperating processes, all on 127.0.0.1. The same code runs in dev and production; only how it is launched and where it writes differ.

Desktop app (Tauri)Rust shell + React UI (ekko-ui/). Picks a free port and a random 32-byte token, then spawns or attaches to the backend. Passes URL + token to the UI over IPC, never in a URL or the bundle.
▼ HTTP + one WebSocket (/ws/status), token in header / subprotocol
Backend (FastAPI, one process)backend/. Settings DB, keys, chat route, memory API, status bus, update check, memory spin-cycle thread. Supervises the listener.
▼ child process, restarted on crash (capped exponential backoff)
Voice listenerlistener/vad_listener.py. Microphone → VAD → wake word → speaker check → Whisper → routing → execute / LLM fallback → TTS. Pushes state to POST /api/status/push; receives UI commands (Wake button) by long-poll GET /api/listener/next.
Text chatThe app's chat panel calls POST /api/chat → chatbot/chat_listener.py's _handle_text_command. Same decision path as voice, no audio stages. Tagged source="chat".
HandlersPowerShell / shell scripts in scripts/<os>/ and personal/scripts/<os>/. The only place a process is started (routing/execute.py).
Nothing reads stdinOn Windows a thread blocked on a stdin pipe deadlocks later native DLL loads (torch, onnxruntime). Control goes over HTTP instead.

One backend, one listener

The backend writes runtime.json (port, token, PID, version) to the data folder, owner-readable. On launch the app looks there first. If a healthy backend of the same version exists (for example the sign-in task's), it attaches. A different version is asked to shut down and a fresh one starts. A backend the app started is stopped via POST /api/shutdown on exit, so the listener stops cleanly too, and it exits on its own if the app's PID dies.

3. The voice pipeline

Each stage runs only if the one before it passes, so the expensive steps never run continuously. The two security checks (real trigger, real user) happen before any transcription or command matching.

Microphone → Silero VADAlways on, 512-sample chunks (~32 ms). Turns audio into speech start/end events.
▼ every chunk also feeds the wake-word model
Wake word: openWakeWord, custom "hey ekko" modelTrained with openWakeWord's open pipeline from synthetic samples. Manual alternative: hotkey (default Ctrl+Alt+W) jumps straight to active listening; hard-stop hotkey (Ctrl+Alt+Q) stops TTS and returns to idle.
▼ wake segment ends
Speaker verification: SpeechBrain ECAPA-TDNNChecked on the wake-word clip (threshold calibrated for that length). A match arms active listening for the active window; a mismatch drops to idle. A looser check on the command segment only rejects non-user audio.
▼ ack played, mic gated until playback + room-decay tail finish (avoids hearing itself)
Segment screening, then faster-whisper transcriptionLong enough, from the enrolled speaker, and Whisper-confident. A failing segment is discarded and listening continues. Model auto: medium on CUDA, small int8 on CPU, half the CPU cores.
▼ transcript
Router → matched? → execute handlerSection 4.
▼ NO_MATCH only
LLM fallback (one call) → spoken answer or validated commandSection 5.
▼ text to speak
Piper TTS (local) or OpenAI speech (optional)Synthesised at runtime through one code path, never written to disk.
Audio never leaves the computer. Only the text of a request EKKO couldn't handle itself goes to the LLM you picked (plus conversation context, section 6). Choosing OpenAI for speech also sends spoken replies there.

It can never reach execute.py. Known limits: negation ("close X" scores like "open X"), one intent per utterance.

5. How LLM calls are made

The LLM runs only after the router returned NO_MATCH. There is exactly one entry point, attempt_with_failover() → attempt_fallback() (llm_fallback/brain/), used by voice, chat, and each provider's CLI.

1. Callers gather contextDomain match → composed system instruction. memory_context (long-term). short_memory (follow-up session). gather_context() → 24h day block + archive keys.
▼
2. attempt_with_failoverBuilds the chain from llm.failover_order starting at the chosen provider; skips providers in cooldown (default 120 s); rebuilds domain override per provider.
▼ per provider
3. Optional live-web researchbrain/research.py: only if enabled, no provider-side search, and a domain with research.yaml or a current-events phrase. Page text is passed as untrusted web_research.
▼
4. build_prompt + system instructionSystem = BASE_CONTRACT.md + optional <provider>_delta.md (+ domain guardrails/persona/knowledge). Per-call payload JSON: transcript, closed intents list, memory, conversation_24h, archive_index, web_research, short_memory, sandbox listing for file-ish requests.
▼
5. provider.call() (transport only)Returns raw text + usage + latency. Spend caps checked before sending (ProviderBlocked).
▼
6. Parse + validateparse_result → validate_pick re-checks any intent against a fresh load of intents.yaml. A rejected pick triggers one retry telling the model to answer directly. Transcript slots are rebuilt only from words the user actually said.
▼
7. FallbackOutcome + loggingCommand bundle, or spoken answer, or neither (noise). Usage and cost logged per provider; context metrics logged.

The reply contract

{"intent": "<name|null>", "slots": {}, "answer": "<text|null>", "urls": [],
 "follow_up": "<grounded next step|null>",
 "memory_candidate": {"text","category","confidence"} | null,
 "recall": [], "reason": "<short>"}

Exactly one of intent / answer may be non-null. An answer never produces an IntentBundle, so it has no path to execute(). recall non-empty means "fetch these archive days and ask again" (section 6). Voice answers are one or two plain sentences; chat answers may use markdown.

  • What triggers a hop: transport failure (503, timeout, unreachable, missing key) or a spend-cap block. A clean "no answer, no command" is noise and is not retried elsewhere.
  • Cooldown: a failed provider is skipped for failover_cooldown_s (120 s default), in-process only. If every provider is cooling down, the whole chain is tried anyway.
  • Order: settings DB section llm (failover_order, validated on save); a provider left out is never a target. failover_enabled=false disables hopping.
  • Cost accounting: each paid provider computes cost from token usage (unknown models priced high, not free) into logs/<provider>/usage_summary.json; the cap is checked before each call. A call in flight can't be cut off, max_tokens bounds it.
  • Logs: logs/<provider>/fallback.jsonl per attempt, logs/failover.jsonl for handoff / skipped / recovered / exhausted.
  • Other LLM caller: scripts/daily_briefing.py uses Gemini's raw generate_content directly, outside the intent contract. The memory summarizer (brain/summarize.py) uses the same provider order and spend accounting.

Adding a provider: write <name>/provider.py (transport only, raise ProviderError), register_provider(), add a row to catalog.py, add usage fields in backend/routers/overview.py. tests/test_catalog.py fails if these disagree.

6. Memory

Three separate stores with different jobs. The context window is protected by keeping recent history whole, old history as one-line keys, and long-term facts few.

Long-term factsmemory/MEMORY.md. Plain, hand-editable, sectioned markdown (Identity, Preferences, Active Projects, Recent Events, Known Facts, Open Threads). Sent as memory in every prompt.
24h day logmemory/day_log/YYYY-MM-DD.jsonl. Every exchange (answers, commands, unrecognised). The last 24h is sent as conversation_24h.
Archivememory/archive.json. One entry per past day: key date | short summary, value {summary, topics, turns, details}. Only keys are sent by default.
Follow-up turnmemory/short_term.json. One in-flight turn (question, answer, follow-up) for the active session only. Soft-deleted to logs/short_memory.jsonl when the session ends.

Worth matrix (what is worth archiving)

Each distinct user phrase scores once by how the turn was handled. Repeating one phrase is a generic pattern and does not add up. A request of six or more words (other than a miss) gets +1.

Turn kindPathWeight per distinct phrase
answerLLM fallback answered3.0
commandDeterministic route matched0.5
unrecognizedNo match, no answer0

Archive when total ≥ MIN_WORTH = 3.0: one real LLM exchange, or about six different commands. Ten "volume up" commands score 0.5. All three constants (KIND_WEIGHT, LONG_PHRASE_*, MIN_WORTH) are in spin_cycle.py. A skipped day is deleted, not recoverable. Intent-level weighting is not done because command turns don't record their intent.

Recall (reaching old days)

If the user refers to a past day, the model replies with up to 3 index keys in recall and null intent/answer. attempt_fallback fetches them (capped at 1500 est. tokens; a key matches by its date prefix) and calls the same provider once more with recalled_archive attached. At most one extra call, only on those turns. Chosen over embeddings because a key is readable in a log; if keys pass ~200 or recall_hits shows misses, embed the keys and pre-filter.

Long-term write policy

A model's memory_candidate is never written automatically. propose_and_score() (pure decision) applies, first match wins: explicit "remember…" request (checked against the raw transcript) → correction or stated preference → fact seen on a second similar sighting (similarity ≥ 0.75, in-memory pending cache, 1 h TTL, resets on restart) → tied to an active project → otherwise reject. Every decision, accepted or not, is appended to memory/logs/decisions.jsonl. The UI can add/edit/delete long-term lines (409 on stale edits); an add skips scoring.

Memory logs and tuning

  • logs/context_metrics.jsonl: one line per LLM call: day turns/tokens, truncated_turns, budget_hit, archive keys sent, recall hits, prompt size, latency, real provider usage.
  • logs/spin_cycle.jsonl: one line per day attempted: turns/tokens in, key, summary tokens, provider, ok/error (and now skipped/worth).
  • Knobs: TOKEN_BUDGET, ANSWER_CHAR_CAP (day_log.py); KEY_CAP, FETCH_TOKEN_CAP (archive.py). Tune from real metrics.
  • UI Memory panel: Today, Archive, Long Term, Follow-up tabs; API under /api/memory/*.
Privacy: the last 24h of everything said is stored on disk and sent to the LLM provider on each fallback call, and long-term facts are re-sent on later calls. Delete a day file or an archive entry (or use the panel) to forget it. Status: the day-log / archive / spin-cycle work is currently uncommitted in the working tree.

8. Security model

ThreatControl
Another machine reaches the APIBind 127.0.0.1 only; reject other Host headers.
Another local processPer-launch token on every request; lives in memory, the app, the backend, and owner-only runtime.json.
A web page calls the APIOrigin must be the app's origin; CORS allows only that.
Token leakageHeader (not URL); WebSocket subprotocol; request logging off.
App used to run codeWebview has no shell/fs/network permissions beyond the local API; strict CSP.
Voice runs arbitrary codeClosed intent set → bare-name handler in scripts/<os>/ → no shell → re-checked at run time. LLM picks are re-validated against a fresh intents.yaml; LLM answers cannot reach execute().
Prompt injection via web researchPage text labelled untrusted; "evidence, not permission"; domain guardrails still apply.
Tampered updateUpdate signature verified against the embedded public key.
Compromised dependencyHash-locked installs, CI pip-audit, CodeQL, Scorecard, Dependabot.

Known limits: the token is readable by any process as the same user; the installer is unsigned (SmartScreen warns); no liveness/replay check on speaker verification; destructive intents need an explicit design before any are added.

10. Other things worth knowing

  • Design rule: deterministic first. Don't add intelligence where a simple rule already works. Zero budget: every default dependency must be free.
  • Startup time: backend starts in under a second; the routing model loads on first use and warms in a background thread (chat.warm).
  • Duplicate models: chat and the listener each load their own routing model. Next performance steps: one process owns models; stream LLM replies into TTS; choose Ollama by hardware.
  • UI: one shared WebSocket for status and reports; panels for General, Models, Routing, Memory, Briefing, Hotkeys, Help.
  • Research tabs: an open-ended answer can open a Brave tab with the query plus up to 3 URLs (best-effort, never affects the spoken reply; --no-research-tabs disables).
  • Daily briefing: scripts/daily_briefing.py with config/daily_briefing.yaml.
  • Flags worth knowing: --no-execute (route and speak, run nothing), --no-llm-fallback, --no-verify, --skip-wake (threshold tuning); backend: --no-listener / EKKO_NO_LISTENER=1.
  • Not yet: macOS/Linux installers, app-side speaker enrolment, signed installer, non-English, partial updates (each update is the full ~250 MB), the backend not restarting itself right after an update.
  • Source-of-truth docs: docs/DESIGN.md, docs/ARCHITECTURE.md, docs/HOST_PROTOCOL.md, memory/README.md, llm_fallback/README.md, routing/README.md.
